## 原則
兩期比對先做實體配對，沒有配對上的稱為「不再收錄」而非「被移除」；移除連結的情境分析要標明是模型，沒有容量資料就不宣稱壅塞。

## 症狀
- 拿兩年份的行道樹（或店家、設施）名冊相減，就發文說「今年砍了 X 棵樹」。
- 舊名冊有、新名冊沒有的點，直接在地圖上標成「被移除」。
- 用最短路徑重算「封掉這座橋」的結果，被讀成「真實尖峰會塞多久」的預測。

## 原因
- 靜態點位只回答「哪裡有」；有兩期才能問「哪裡變了」。但兩期比較不是兩份表直接相減，要先確認是不是同一個實體。
- 一筆紀錄不再出現，可能是：真實移除、移植或死亡；漏登或調查範圍改變；重新編號或格式改變；座標誤差與配對失敗；資料尚未更新。
- 移除網路中一條連結再重算路徑，是情境分析；沒有容量、時段需求與動態選路時，它反映的是自由流條件下的路徑成本，不是壅塞預測。

## 解法
**兩期比對**
1. 先寫清楚兩期的年份、涵蓋範圍、調查口徑與欄位定義。
2. 有跨期穩定 ID 最好；沒有就用空間距離加屬性（種類、道路、尺寸）配對，並記下配對門檻與可能的錯配。ID 漂移的常見情況見 [01-14](../01-taiwan-apis/01-14-semantics-drift-and-upstream-loss.md)。
3. 結果分四類，用資料語言命名：
   - 兩期皆有：Matched / Persisting
   - 新一期才有：Newly recorded（名冊新增）
   - 舊一期有、新一期無：No longer recorded（不再收錄）
   - 屬性改變：Updated
   一開始就不要寫「新增／砍除」。
4. 比較時看比例與組成，不只看件數：少 100 與少 60，要看原本各有多少；消失的是成熟大樹還是新植小樹，意義不同。
5. 解釋原因前先排除資料因素，再找外部證據（工程公告、維護或移除紀錄、災害時間、街景、抽樣現勘）。疊圖重疊（例如道路工程範圍）只是可能解釋之一。
6. 措辭對照：
   | 不建議 | 較嚴謹 |
   |---|---|
   | 今年砍了 X 棵樹 | 兩期名冊中有 X 筆未配對／不再收錄，原因待確認 |
   | 這一帶沒有樹 | 在這份名冊的涵蓋範圍內，此區紀錄較少 |
   | 因為施工所以樹消失 | 施工是可能解釋之一，需比對工期與異動紀錄 |

**移除連結的情境分析**
1. 重要性同時看依賴量（多少流動經過）與替代性（失效後有沒有可行替代）；「影響很多人一點點」與「影響較少人很多」都值得關注（關係型別見 [00-05](00-05-eight-relationship-types-and-spatial-vs-system-proximity.md)）。
2. 損失指標例：總旅行時間增量 Σ qᵢ·Δtᵢ（qᵢ＝起訖群組旅次量，Δtᵢ＝封閉後減基線的每趟增量），單位依旅次母體寫成「人・分鐘」或「車・分鐘」。完全到不了的旅次要另外定義，不能當成有限的繞行時間。
3. 成果圖分三個標籤：觀測、簡化模型（例：固定 OD、固定速度的最短路徑）、未來模擬（容量、時段、動態選路）。沒有容量就不宣稱壅塞時間。
4. 寫明模型含不含 OD、速度、容量、多運具，並確認圖面與軟體輸出一致。

## 怎麼偵測
- 通用：兩期差異圖的圖例用「砍除」「新增」而不是「不再收錄」「名冊新增」；沒有交代配對方法；情境分析圖沒有標示「情境」或「模型」。
- 搜尋（文字）：`砍了|被移除|消失了` 出現在只有名冊比對的段落；`會塞|塞車.{0,6}(分鐘|小時)` 出現在沒有容量資料的最短路徑分析。
- 搜尋（程式）：兩期 merge 只用 `id` 欄位直接 anti-join，沒有空間或屬性配對的後備（pandas、SQL）。

## 出處
- Record linkage／entity resolution 的一般方法（跨期比對同一實體，處理 ID 與位置誤差）。
- 網路韌性：network redundancy、criticality、accessibility loss 的一般概念。
