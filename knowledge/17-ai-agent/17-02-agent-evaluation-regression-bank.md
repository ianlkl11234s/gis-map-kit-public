## 原則
用固定題庫做回歸驗收：先量測基準，失敗先分類，一輪只改一類，標準答案先用獨立程式驗算，每修一項補一題回歸題，並且一定要接真地圖跑一輪。

## 症狀
- 改了提示或工具之後，覺得 agent「好像變好了」，但說不出好在哪、有沒有別的題變差。
- 題庫說 agent 答錯，查了半天才發現是題庫的標準答案算錯。
- 工具測試全綠，接上真的地圖後使用者卻看不到結果。

## 原因
agent 的行為有隨機性，又同時受提示、工具、資料、地圖前端影響。沒有固定題庫與分類，就只能憑印象；一次改很多類，也無法知道哪個改動有效。

## 解法
1. **固定題庫**：用使用者口吻寫 20–30 題，涵蓋找資料、計數、排名、比較、無資料、資料陷阱等題型。每題寫預期資料、預期數字（含誤差與單位）、必須出現的提醒。
2. **標準答案先用唯讀查詢驗算並存檔**（SQL 或另一套統計程式），不用被測工具自己的程式驗自己。agent 和題庫答案不同時，兩邊都驗：題庫錯就修題庫，不放寬檢查。
3. **自動檢查分維度**：找對資料、數字一致、語氣與格式（[17-03](17-03-agent-answer-format.md)）、提醒、上圖。每個維度各自計分，才看得出是哪一類壞掉。
4. **先量測基準**，再改。每題跑 2 次以上看變異；不穩定的題分開列出。
5. **失敗先分類**：題庫、資料（缺使用須知）、提示／skill、工具、測試架構本身。**失敗先重跑一次，重跑會過的先當作環境或隨機性問題**，只有穩定重現的才改程式。
6. **一輪只改一類**，改完重跑受影響的題，並重跑其他題庫確認沒有退步。
7. **每修一項就補一題回歸題**，把這次的失敗變成以後的守門。
8. **一定要有「接真地圖」那一輪**：倉庫工具分數高，不代表使用者看得到；上圖要以回讀為準（[17-01](17-01-agent-map-control-rules.md)）。每題開始前清掉上一題留下的圖層與鏡頭。
9. **記錄成本**：每題耗時、回合數、花費；回歸測試很貴，不進每次 CI，在改提示、改工具、換資料版本後跑。

## 怎麼偵測
- 通用：改提示或工具的 PR 沒有附任何前後分數；題庫的標準答案沒有驗算紀錄；只跑工具單元測試，沒有端到端的 agent 測試。
- 搜尋：題庫檔（`questions*.json`）的預期值沒有對應的驗算檔（`verification/`、`*.sql`、`*.py`）；檢查程式只比對最終回答，沒有看工具呼叫紀錄（適用 stack：any）。
