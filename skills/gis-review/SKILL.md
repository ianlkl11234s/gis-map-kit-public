# gis-review：掃描專案找改善點

知識庫在本 plugin 根目錄的 `knowledge/`（本檔往上兩層）。**全程唯讀**，不改使用者的檔案。

## 步驟 1：認識專案（自己做，幾個工具呼叫內完成）

- 讀 package.json（或同等檔案）判斷 stack：mapbox-gl／maplibre-gl／leaflet／deck.gl／three／openlayers，以及 React／Vue／純 JS。
- 找地圖初始化、圖層定義、資料載入的位置。
- 問使用者一句：這是給誰用的（研究、課堂、公開網站）、手機重不重要。公開網站才檢查 SEO 與嵌入。

## 步驟 2：派唯讀子代理掃描

讀各主題的 `knowledge/<topic>/_index.md`，依 stacks 欄篩掉不適用的卡（stacks 不含該 stack 也不是 any 的跳過）。把剩下的卡依主題分成最多 3 組，用 `gis-auditor` 子代理平行掃描。每組給它：專案路徑、stack、要檢查的卡片 id 清單，以及 `knowledge/` 的**絕對路徑**（本 skill 的 base directory 往上兩層；子代理不知道 plugin 裝在哪）。子代理照每張卡的「怎麼偵測」搜尋，回報命中的檔案與行號。

建議分組：
1. 資料與正確性：01、06、12（API 接法、格式、缺值、時區、領域資料）
2. 畫面與互動：05、08、09、11、14（色階、圖例、多圖層、RWD、分享、尺度與密度）
3. 效能與維運：03、04、07、10（時間軸、動態效果、效能、金鑰、部署）
4. 作者品味：13（併入第 2 組即可，不另開子代理）

## 步驟 3：報告

依嚴重度分三級，每項寫：問題、證據（檔案:行號）、建議怎麼修、對應卡片 id。

- **必修**：會讓資料錯、壞掉或外洩。例如缺值畫成 0、時區錯、金鑰進前端 bundle、開放資料含個資照樣顯示、沒有 loading／錯誤狀態、沒有 attribution。
- **建議**：使用者體驗或維護性明顯變好。例如沒標資料時間、手機互動不能用、圖例和顏色不同源、重繪過多。
- **可加分**：分享網址、嵌入、SEO、動態效果、無障礙。

另列兩類：
- **看不出來**：靜態掃描無法判斷的項目（例如手機實機手感、實際載入速度），寫出要怎麼人工驗。
- **沒有偵測到問題的主題**：一句帶過，不逐項列。
- **與作者品味不同**（獨立一段，不算問題、不進三級）：照 `13-author-taste` 各卡的「怎麼偵測」（主要是 13-07 反面清單）列出差異，例如衛星當預設卻沒有看地表的需求、載入 web font、圓角大於 8、時間軸自動播放。每項寫一句作者偏好的理由，並說明「有自己的理由可以不改」。

## 步驟 4：下一步

問使用者要先修哪幾項；使用者同意後才動手，修的時候依卡片解法做。

## 原則

- 只有偵測到證據才列為問題；卡片寫「僅限某架構」的偵測，不適用時不列。
- 不把 General 類卡片的建議寫成「一定要做」，放在建議或可加分。
- 報告不貼出使用者的金鑰值；看到疑似金鑰只寫檔案與行號，值用 <REDACTED>。
